# 日志与排查

本机工作台顶部的“运行日志”进入 `/logs`。此页面只读取记录，不调用模型，不重新运行任务。

## 流程记录

每轮 `reports/workflows/run-.../` 或 `resume-.../` 目录是一个追踪单元：

- `workflow.json` 保存模式、样本、预算、各阶段开始与结束时间、错误和停止原因。
- `events.jsonl` 保存阶段开始、完成、失败、预算占用和人工复核等事件。
- 各阶段 `.log` 保存对应子进程输出；模型回答、证据与反馈文件留在该轮目录。

日志页覆盖失败及尚未生成复核表的流程。为了限定读取量，最多检查 100 个流程目录；事件只读最后 64 KiB 中的至多 100 行。损坏的状态文件与事件行会计数显示，不补造记录。历史流程档案不会被自动清理；大视频证据按实际需要手工备份或归档。

新 live 流程还保存 `plan.json` 和 `metrics.json`。日志页展示任务计划及数据计算的执行/跳过理由，旧流程不补造计划。Windows 临时文件占用时，原子 JSON 替换最多尝试 6 次、累计等待 0.62 秒；只重试本地替换，不重新执行工具或模型调用。持续失败仍向调用方报错，原文件不被删空。

启用语义返修后，日志页另列检查对象、反馈理由、轮数和停止原因。每个修正/再次验证阶段都独立预留一次模型预算；缺证或预算不足会留下停止事件。整体 `awaiting_human_review` 表示自动处理已经结束，具体是否缺证须看 `refinement.status`，不表示模型已经正确完成所有判断。

耗时由已保存的开始、结束时间计算；未结束时显示空值。模型阶段尝试次数不能直接用来计算费用。旧目标的流程保留原样，不代表新目标的结果。

## 工作台请求记录

网页启动任务另有 `reports/web-jobs/job-.../events.jsonl`，保存计划、启动、完成或失败的 UTC 时间与追踪编号。HTTP 日志覆盖样本登记、计划和启动接口。工作进度与失败详情仍由 `reports/workflows/run-web-.../` 中的原有阶段记录提供；工作进程日志保存在对应网页任务目录。新分析失败会将阶段 `run.json` 标为 failed，网络中断的已有部分输出另存。详见 [网页启动](web-start.md)。

`reports/review-server/requests.jsonl` 为应用处理的 GET/POST 响应记录 UTC 时间、请求编号、请求方法、白名单接口名、HTTP 状态码和耗时（毫秒）。响应头 `X-Request-ID` 可用于定位请求。HTTP 解析层拒绝的畸形请求不在此日志范围内。

不记录查询参数、请求/响应正文、API 密钥、会话令牌、IP 或用户代理。未知接口统一记为 `[other]`。单个日志上限为 1 MiB，最多保留 3 份轮转备份。页面只展示当前文件末尾的 50 条请求，早期轮转记录仍可在本地查看。

工作流日志页面只返回必要字段，隐藏 URL、本地绝对路径和常见凭据格式。这是辅助脱敏，不能保证任意第三方错误文本都不包含敏感信息；原始档案仅保留在本机，不上传仓库。历史日志不会被改写。

## 排查步骤

1. 在日志页筛选“失败”，按流程编号找到停止阶段。
2. 看停止原因、阶段耗时与事件顺序。若是页面请求问题，按状态码和请求编号定位。
3. 需要更详细信息时在本机打开对应阶段日志；分享之前检查正文并移除凭据和私人材料。
4. 修复后按需要启动新流程，保留原失败记录。不因页面刷新而自动重试模型。

## 对照评估记录

每个 `reports/evaluations/eval-.../events.jsonl` 记录准备、人工冻结、计算报告的状态、UTC 时间、追踪编号和耗时；错误复用脱敏处理，不记录标注正文。单文件超过 256 KiB 后保留一份旧日志。证据和标注指纹保存在同包文件中，计分时重新核对。该入口目前是命令行工具，工作台日志页暂未汇总评估记录。

`reports/`、本地配置和个人样本由 `.gitignore` 排除。GitHub 只备份程序、通用示例和文档，不备份实际复盘证据。
