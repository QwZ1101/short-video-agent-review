# 受控返修与补证停止

验证之后，程序根据总结和逐条检查的状态决定下一步。验证员的理由仍需核对，不能作为新的事实证据。

| 条件 | 行为 |
| --- | --- |
| 任意项为 `insufficient_evidence` | 优先停止，保存待补证事项；即使其它项需修正也不调用模型 |
| 所有项为 `supported` | 停止并进入人工复核，不自动接受 |
| 有 `revise` 且轮数、预算足够 | 用同一批冻结证据修正初稿，再独立验证一次 |
| 剩余调用预算小于 2 | 不开始半轮返修，留下预算不足原因 |
| 达到最多轮数 | 停止并保留未解决项 |
| 返修稿总结及建议均未变化 | 不再重复验证，保留原检查结果 |
| 网络中断、无效结构、未知引用或验证输入不一致 | 本轮失败并留档，不自动重试，不生成已通过结果 |

每轮包含一次修正和一次再次验证，最多两轮。修正必须保留建议 ID，不能更换证据，不能改写已获支持的条目。程序只强制结构和来源边界，不保证模型修正后的语义正确。再次验证所检查的是修正员输出；验证员自己的 `revised_review` 仍为未再次核验的候选稿。

## 新任务

默认行为仍是两次模型阶段、无自动返修。显式启用一轮返修：

```powershell
python run_workflow.py --mode live --sample data/samples/tutorial-002.json --max-model-calls 4 --max-repair-rounds 1
```

这里的 4 是**本轮总预算**：原分析 1 + 原验证 1 + 可选修正 1 + 可选再次验证 1。两轮需至多 6 个阶段预算。即使启用返修，证据不足时也不会用完预算。

## 已有结果

先看调度决定（不占用继续次数、不调用 API）：

```powershell
python refine_workflow.py --workflow-dir reports/workflows/run-示例编号 --dry-run
```

为已有结果创建独立继续记录：

```powershell
python refine_workflow.py --workflow-dir reports/workflows/run-示例编号 --max-model-calls 2 --max-repair-rounds 1
```

这里的预算是**追加预算**。界面同时显示来源流程已尝试次数，不能把来源调用遗漏为零成本。示例编号需要替换为真实目录名。

每个来源流程只允许创建一次继续记录，使用排他创建的 `refinement-claim.json` 防止双击与并发重复启动。继续记录不允许再作为来源叠加预算。来源必须是尚未人工接受、没有执行过语义返修的 live/verify 流程。目标或目标版本发生变化时，应重新分析；不能沿用旧目标结论。排他记录在失败后仍保留，程序不会自行删除以重试。

## 档案与补证

`workflow.json` 的 `refinement` 保存轮数、逐项反馈、各轮来源和停止原因；`repair-tasks.json` 保存停止时待处理事项。各轮修正输入、提示词、反馈、原始模型回答和验证结果放在 `refinement/round-N/`；`events.jsonl` 保存阶段事件与预算预留记录。

缺证时整体流程进入人工复核入口，界面显示“等待补证 / 人工复核”，没有自动生成用户确认结果。补充音频说明、后台统计或相应原始材料后，应登记到样本并启动新流程。当前没有自动采集补证，也没有自动把人工补证合入旧轮次。

一次验证格式修复仍由 `resume_workflow.py` 单独处理。它只修复正常返回但结构无效的回答，不能用来重试网络失败或替代这里的语义返修。

## 验证边界

自动测试使用合成反馈覆盖修正后支持、仍需修正、证据不足、无变化、预算不足及网络失败路径；不能据此证明建议质量提升。实际案例已验证缺证停止路径，正向语义改善仍需要真实案例与人工标注评测。
